# Rain Deals database manager

This JavaScript Worker hosts the manager directly on Cloudflare. It uses the existing private TiDB RPC binding and API Worker service binding. There is no Render origin or Render dependency.

Implemented: product creation/editing, API visibility, delivery options, preorder, bulk pricing, account append/replace/clear, archival, provider configuration, promocodes, custom rates, bans, ticket edits and API key revocation. Orders, deposits, API orders and referrals can be viewed and searched, with pagination. Eligible manual/hybrid orders can be fulfilled from uploaded account inventory or entered delivery details. Inventory consumption and order completion are committed together; the completed order is then sent or queued through the existing API Worker delivery service. Provider credentials and account inventory are excluded from listing responses.

The manager maintenance toggle reads and writes maintenance_settings.enabled in the shared database. The main Telegram bot checks this value on each incoming update, so changes apply without restarting the bot. An optional manager note is stored separately and is not shown to customers. Provider synchronization, automatic refunds, deposit crediting, broadcasts, and webhook changes are unavailable. The delivery connection check only checks the existing API service.

Order fulfillment calls the existing `raindeals-api` Worker through its private service binding. Set `DELIVERY_BRIDGE_SECRET` on the Manager Worker to the same secret already configured on the API Worker. Do this from this directory with `npx wrangler secret put DELIVERY_BRIDGE_SECRET --config .\wrangler.production.jsonc`; enter the existing value when prompted. The API Worker also checks that the acting Telegram ID is in its delivery admin allowlist. A recipient who has not started the Delivery Bot receives the queued order after they press `/start` there. Re-checking delivery is idempotent; the Delivery Worker prevents a second send after a confirmed delivery.

Completed order cards show only **View order details**. That window includes submitted buyer email/text/contact details, delivery recipient and job state, recorded send times, and admin activity from both the bot audit table and the manager audit table. Missing historical information is shown as not recorded. Future web fulfillments also record the fulfilling admin's session start time. Submitted order information is read directly from the shared database and requires no bot token. Emails, text, and contacts display in the details window. Photos display as submitted attachments with their stored Telegram file reference; the manager does not download images from Telegram.

Grant `orders` and `orders_write` for fulfillment; grant `products` and `products_write` for inventory uploads. The separate `delivery_secrets` permission plus `orders_write` allows viewing/correcting saved delivery credentials. Corrections never resend or modify existing Telegram messages, cannot change the buyer or financial status, are audited without recording credentials, and are blocked while a delivery is queued, sending, or uncertain. Run `node order-checks.mjs` for the isolated order-detail, permission, and correction checks.

Sign-in normally requires the manager username/password and approval from an allowlisted Telegram admin. Alternatively, an admin can request a private, single-use Manager Web link from the bot; it expires in two minutes and starts a 60-minute session without another Telegram prompt. Choose a 60- or 120-minute session for the normal sign-in flow. Sessions use Secure/HttpOnly/SameSite cookies, and state-changing routes require CSRF and same-origin checks. Login attempts are limited to five per minute per IP to slow password guessing; manager data reads and writes have no per-admin request quota. Product, order, deposit, user, provider, inventory, and other sensitive routes require Telegram step-up approval every 30 minutes. In a private chat, /forcekill (or /kill) revokes all sessions and makes every manager URL show only a force-lock message until /unkill is completed in the verification bot. /unkill asks for the manager password; the bot attempts to delete the password message immediately. The API Worker receives that password only as the MANAGER_UNLOCK_PASSWORD secret, populated from local MANAGER_PASSWORD by deploy_forcekill.py. Only IDs in MANAGER_ADMIN_IDS can use these commands. The Worker returns table-specific fields, omits account inventory and provider credentials from ordinary list responses, and audits manager changes without storing submitted values.

The bot's private one-time Manager Web link is also cleaned up: its Telegram button is removed immediately after successful use, or by the one-minute scheduled cleanup after the two-minute expiry. Apply `migrations/004_manager_link_card_cleanup.sql` to the same TiDB database before deploying these changes. Set `MANAGER_TELEGRAM_BOT_TOKEN` on both Manager Worker environments to the main RainDeals bot token (the bot that sends the link card), using `npx wrangler secret put MANAGER_TELEGRAM_BOT_TOKEN --config .\wrangler.production.jsonc` and `npx wrangler secret put MANAGER_TELEGRAM_BOT_TOKEN --config .\wrangler.jsonc`. The token is stored as a Worker secret and is never returned to the browser.

Deploy using python deploy.py from this directory. It reads the root and manager_web .env locally and uploads only MANAGER_USERNAME and MANAGER_PASSWORD as Worker secrets, without displaying them. It uses a temporary file which is removed afterwards. Database credentials remain in the private TiDB service. The Worker initializes manager-owned sessions, login preferences, step-up grants, login lockout, settings, login-attempt, and audit tables; the database user needs CREATE permission. Existing application tables must already exist.

Local checks: node checks.mjs
Worker logs: npx.cmd wrangler tail --config .\wrangler.jsonc

No local server or tunnel is needed after deployment. This does not alter the main Telegram bot or its Render service.


For partial hybrid orders, the manager fulfills only `manual_pending_quantity`, appends delivery data to the already delivered accounts, and keeps reserved order capacity from being deducted twice. Products expose `manual_fallback`; account uploads preserve the separately configured capacity when this flag is enabled. Deploy the updated Render bot first to apply the new fulfillment columns through its startup schema helper, then deploy this manager. The separate Cloudflare public API's order-creation path is not migrated by this manager deployment.
